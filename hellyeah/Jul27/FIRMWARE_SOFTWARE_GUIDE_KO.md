# 양팔 스윙 측정 및 균형 피드백 시스템

> 문서 기준: 2026-10-09 · Jul27 펌웨어의 비동기 업로드 및 알림 팔 기록 기능 적용 버전

> 2026-10-24 수정: 두 버전의 피드백 비교 구간을 5초, 상대 데이터 유효 시간을 6초로 변경했다. 이 문서의 나머지 구조 설명은 작성 당시 버전 기준이며, 이후 원본 펌웨어에 추가된 클라우드 제어는 `CLOUD_CONTROL.md`를 참고한다.

## 1. 시스템 개요

이 시스템은 왼팔과 오른팔에 각각 장착한 보드로 팔의 움직임을 측정하고, 양팔의 활동량을 비교해 상대적으로 움직임이 적은 쪽에 알림을 주는 장치다. 각 보드는 자신의 센서 데이터를 직접 처리하며, 상대 보드와 최근 측정값을 교환한다. 측정 결과는 Google Sheets에 팔별로 기록된다.

전체 소프트웨어는 세 부분으로 구성된다. **보드 펌웨어**는 센서 측정, 스윙 판단, 무선 통신과 알림 출력을 담당한다. **보드 내 웹 페이지**는 알림 활성화와 민감도 조절, 상태 확인, 원시 데이터 수집에 사용한다. **Google Apps Script**는 보드가 보낸 데이터를 받아 스프레드시트에 저장한다.

두 보드는 독립적으로 동작한다. 왼쪽 보드가 오른쪽 센서를 직접 읽거나, Google Sheets가 실시간 알림 대상을 결정하는 구조는 아니다. 각 보드가 ESP-NOW로 받은 상대 팔의 값과 자신의 값을 비교해 **자기 보드의 알림 출력**을 결정한다.

```text
왼팔 IMU → 왼쪽 보드 ←── ESP-NOW ──→ 오른쪽 보드 ← 오른팔 IMU
                │                         │
          자기 팔의 알림 출력        자기 팔의 알림 출력
                │                         │
                └──── Wi-Fi / HTTP ───────┘
                              ↓
                       Google Apps Script
                              ↓
                        Google Sheets

같은 네트워크의 브라우저 → 왼쪽 보드의 제어 페이지
```

## 2. 하드웨어별 펌웨어

현재 설명 대상은 진동 모터용과 피에조용 두 가지 버전이다. 측정, 양팔 비교, 업로드 및 알림 기록의 기본 구조는 공통이며, 출력 장치와 일부 센서 구성이 다르다.

| 구분 | 진동 모터 버전 | 피에조 버전 |
| --- | --- | --- |
| MCU | ESP32-S3 | ESP32-S3 |
| 움직임 센서 | 보드당 ICM-42688-P 1개 | 보드당 ICM-42688-P 1개 |
| 알림 출력 | GPIO 14의 PWM으로 진동 드라이버 제어 | GPIO 14에서 4 kHz 피에조 구동 |
| 불균형 증가 시 | PWM 출력 강도 증가 | 짧은 소리 펄스의 반복 간격 감소 |
| 추가 센서 | 해당 없음 | MMC5983MA 자기장 센서, I²C SDA 4 / SCL 5 |

IMU는 SPI로 연결되며 핀은 MISO 8, MOSI 9, SCLK 10, CS 11이다. 피에조 버전에는 자기장 센서 측정 기능도 포함되어 있지만, 현재 스윙 및 양팔 균형 판단의 기본 입력은 IMU에서 계산한 스윙 횟수와 거리다.

진동 버전 소스는 이 문서와 같은 `Jul27` 폴더에 있다. 피에조 버전은 야호 프로젝트의 `piezo_version/firmware/Jul27`에 있으며, 상위 `firmware/common`의 공통 헤더도 함께 필요하다. 실제 출력 장치에 맞는 버전을 사용해야 한다. 진동 버전의 보드 주석에는 rev C의 진동 드라이버가 DNP로 표시되어 있으므로, 진동 동작을 확인할 때에는 실제 드라이버와 모터의 실장 여부도 함께 확인한다.

## 3. 센서 측정과 스윙 계산

### 시작과 보정

부팅 시 IMU를 초기화한 뒤 Wi-Fi 연결, 시간 동기화, ESP-NOW 및 웹 서버 설정을 수행한다. 이후 IMU 온도 안정화를 기다리고 자이로 바이어스를 보정한다. 온도 안정화 대기는 최대 45초이며, 자이로 보정은 약 2초의 측정으로 이루어진다. 보정 중에는 보드를 움직이지 않는 것이 중요하다.

현재 Wi-Fi 연결 단계는 연결될 때까지 대기하는 구조다. 따라서 부팅 직후부터 바로 측정 데이터가 올라오는 것은 아니다. 10초 기록 구간은 초기 설정과 보정이 끝난 후 시작한다.

### 스윙 판정

펌웨어는 자이로의 Y축 각속도에서 바이어스를 뺀 값을 시간에 따라 적분해 각도 변화를 계산한다. 가속도 크기 변화와 각속도가 설정된 문턱값을 함께 넘으면 스윙을 시작한 것으로 판단한다. 이후 방향이 반전되거나, 일정 시간이 지난 뒤 움직임이 작아지거나, 최대 지속 시간을 넘으면 스윙 구간을 종료한다.

| 항목 | 기본값 또는 처리 방식 |
| --- | --- |
| 샘플링 목표 | 약 250 Hz; 실제 주기는 루프 실행 시간의 영향을 받음 |
| 스윙 판단 축 | 자이로 Y축 |
| 시작 각속도 문턱값 | 양·음 방향 각각 0.4 rad/s |
| 가속도 변화 문턱값 | 중력 크기 약 9.8 m/s²에서 2.0 m/s² 초과 차이 |
| 스윙 최대 지속 시간 | 1,200 ms |
| 빠른 중복 카운트 억제 | 직전 카운트 후 400 ms 이내 종료된 구간은 카운트하지 않음 |
| 기본 회전 반경 | 0.30 m |

코드의 `count`는 이 알고리즘이 인정한 스윙 구간의 수다. 이를 항상 ‘앞뒤 왕복 한 주기’나 걸음 수와 동일하게 해석해서는 안 된다.

스윙 거리 추정에는 다음 관계를 사용한다.

```text
스윙 구간의 추정 호 길이(m) = |구간 종료 각도 − 구간 시작 각도|(rad) × 회전 반경(m)
```

기록되는 거리는 인정된 스윙 구간들의 호 길이를 합한 값이다. 실제 손의 3차원 이동 경로를 직접 측정한 값은 아니며, 착용 방향과 설정한 회전 반경의 영향을 받는다. 센서 장착 방향 때문에 다른 축을 사용해야 한다면 스윙 계산과 자이로 보정에서 사용하는 축을 함께 맞춰야 한다.

## 4. 양팔 비교와 알림 대상 결정

양팔 비교에는 **약 5초 단위의 피드백 구간**을 사용한다. 각 보드는 이 구간의 스윙 횟수와 거리, 알림 활성화 상태 및 민감도 설정을 ESP-NOW로 전송한다. 두 보드는 같은 Wi-Fi AP에 연결해 같은 무선 채널에서 통신하도록 구성되어 있다.

왼팔의 활동 비중은 횟수 비중과 거리 비중의 평균으로 계산한다.

```text
왼팔 횟수 비중 = 왼팔 횟수 / (왼팔 횟수 + 오른팔 횟수)
왼팔 거리 비중 = 왼팔 거리 / (왼팔 거리 + 오른팔 거리)
왼팔 활동 비중 = (왼팔 횟수 비중 + 왼팔 거리 비중) / 2
오른팔 활동 비중 = 1 − 왼팔 활동 비중

자기 팔의 부족 정도 = 0.5 − 자기 팔의 활동 비중
```

자기 팔의 부족 정도가 데드존을 넘으면 그 보드가 자신의 알림 출력을 활성화한다. 기본 데드존은 `0.055`다. 예를 들어 왼팔 활동 비중이 `0.40`, 오른팔이 `0.60`이면 왼팔의 부족 정도는 `0.10`이므로 기본 설정에서 왼쪽 보드가 알림 대상이 된다. 데드존을 크게 설정할수록 작은 차이에는 반응하지 않는다.

합산 횟수나 거리가 비교에 충분하지 않거나, 상대 보드의 정보가 오래되었거나, 알림이 비활성화되어 있으면 출력하지 않는다. 상대 데이터의 유효성 기준은 6초이며, 실제 출력 반영 시점은 각 버전의 피드백 처리 시점에 따른다. 두 보드의 비교 구간은 하드웨어적으로 동기화되어 있지 않으며, 각 보드가 받은 상대의 최신 구간을 사용한다.

진동 모터는 불균형 정도에 따라 PWM 값을 증가시킨다. 피에조는 최대 70 ms의 짧은 펄스를 사용하며, 불균형이 커질수록 반복 주기가 약 1,000 ms에서 200 ms로 짧아진다. 늦게 시작한 펄스는 남은 활성 시간만 사용하므로 항상 70 ms 동안 울리는 것은 아니다.

알림 활성화와 데드존 설정은 왼쪽 보드가 기준이 된다. 오른쪽 보드는 왼쪽 보드의 ESP-NOW 패킷에서 이 설정을 받아 적용한다.

## 5. 10초 기록과 비동기 업로드

Google Sheets 기록 구간은 피드백 구간과 별도로 **10초**다. 즉, 5초마다 최근 양팔 상태를 비교하면서 10초마다 자기 팔의 측정 결과를 한 번씩 기록 대상으로 만든다.

이전의 동기식 전송 구조에서는 HTTP 요청이 끝난 뒤 다음 10초 대기를 시작했다. 요청에 3~5초가 걸리면 관측되는 전송 간격이 약 13~15초로 늘어날 수 있었고, 요청 처리 동안 센서 측정도 지연될 수 있었다.

현재 구조에서는 측정 루프와 네트워크 전송을 분리했다. 측정 루프는 10초 구간을 닫고 횟수·거리·알림 여부를 큐에 복사한 뒤 다음 구간의 측정을 계속한다. 별도의 FreeRTOS 작업이 큐에 들어온 데이터를 HTTP로 전송한다. 따라서 업로드 시간만큼 측정 구간이 매번 늘어나는 현상을 방지한다.

다만 **10초 측정 구간과 스프레드시트에 행이 도착하는 간격은 서로 다르다.** Wi-Fi 상태, HTTP 처리, 서버의 잠금 대기 등에 따라 행의 도착 시간은 여전히 달라질 수 있다. 현재 시트의 `Timestamp`는 보드의 구간 종료 시각이 아니라 서버가 행을 기록하는 시각이다.

전송 큐에는 최대 12개의 작업이 대기할 수 있고, 별도로 1개의 요청이 전송 중일 수 있다. 측정 기록과 알림 활성화 변경 이벤트가 같은 큐를 사용한다. 큐가 가득 차면 새 기록을 버리고 누락 카운터를 증가시킨다. 오프라인 또는 전송 실패 시에도 해당 작업을 폐기하며, 중복 기록 방지를 위해 자동 재시도는 하지 않는다.

HTTP 외의 작업이 측정 루프를 지연시킬 가능성은 남아 있다. 예를 들어 원시 로그 저장·다운로드나 수동 재보정이 영향을 줄 수 있다. 루프가 늦어지면 실제로 길어진 하나의 측정 구간을 기록하고 다음 기준 시점을 유지한다. 누락된 시간을 여러 개의 정상 10초 구간으로 만들어 기록하지 않는다. 샘플 간격이 100 ms를 초과하면 그 간격의 각도 적분을 건너뛰고 진행 중인 스윙을 취소한다.

## 6. Google Sheets 데이터와 알림 팔 기록

각 보드는 자신의 측정 구간을 다음과 같이 전송한다. 아래 값은 형식을 보여 주는 예시다.

```json
{"arm":"L","count":12,"distance":345.67,"alerted":true}
```

| 필드 | 의미 |
| --- | --- |
| `arm` | 데이터를 보낸 보드의 팔: `L` 또는 `R` |
| `count` | 해당 기록 구간에서 인정된 스윙 횟수 |
| `distance` | 해당 구간의 누적 추정 스윙 거리, cm |
| `alerted` | 해당 구간에 자기 보드의 알림 출력 명령이 있었는지 나타내는 불리언 |

Apps Script는 측정값을 `Data` 시트에 저장하며, 해당 이름의 시트가 없으면 첫 번째 시트를 사용한다. 두 보드의 요청이 겹쳐도 행 추가가 충돌하지 않도록 스크립트 잠금을 사용한다.

| Timestamp | Arm | Count | Distance(cm) | Alerted Arm |
| --- | --- | --- | --- | --- |
| 서버 기록 시각 | L | 12 | 345.67 | L |
| 서버 기록 시각 | R | 15 | 410.20 | None |

위 표 역시 설명용 예시다. `Alerted Arm`의 해석은 다음과 같다.

| 값 | 의미 |
| --- | --- |
| `L` | 이 행의 구간에 왼쪽 보드가 알림 출력을 명령함 |
| `R` | 이 행의 구간에 오른쪽 보드가 알림 출력을 명령함 |
| `None` | 새 펌웨어가 알림 출력 명령이 없었다고 보고함 |
| `Unknown` | 이전 펌웨어의 요청 등으로 `alerted` 정보가 없음 |

알림 여부는 전송 순간의 출력 상태만 보는 것이 아니다. 구간 중 잠깐 발생한 피에조 펄스도 기억하며, 지속된 출력이 기록 구간 경계를 넘으면 양쪽 구간에 반영한다. 같은 밀리초 안에 켜졌다 꺼진 출력 명령도 기록한다.

이 값은 **알림 출력 명령의 기록**이다. 모터나 피에조가 실제로 작동했는지를 별도 센서로 확인한 값은 아니며, 알림 횟수·지속 시간·강도를 저장하는 필드도 아니다. 양팔은 각각 독립된 행으로 기록되므로, 하나의 행에 두 팔의 결과를 합쳐 저장하지 않는다.

새 스크립트는 기존 A~D열을 유지하고 다음 측정 요청에서 E열에 `Alerted Arm` 제목을 추가한다. E열에 다른 제목이 있으면 덮어쓰지 않고 오류를 반환한다. 기존 과거 행은 수정하지 않는다. 기존 행의 알림 정보가 비어 있으면 `doGet` 응답에서는 `Unknown`으로 표시한다.

알림 활성화 변경은 기존과 같이 별도의 `Events` 시트에 저장한다.

```json
{"event":"motor_toggle","state":"off","ts":1700000000}
```

`Events`의 열은 `Received At | Event | State | Board Timestamp`다. 이 이벤트는 알림 기능의 활성화 상태 변경이며, 실제 알림이 발생했다는 뜻은 아니다. 보드 시각은 NTP 동기화 상태의 영향을 받는다. 피에조 버전에서도 호환성을 위해 `motor_toggle`이라는 이벤트 이름을 유지한다.

`doGet`은 팔별 최신 기록을 조회하는 기능도 제공한다. 응답에는 기존의 `arm`, `count`, `distance`, `timestamp`와 새 `alertedArm`이 포함된다. 현재 실시간 피드백 판단은 이 조회 기능 대신 ESP-NOW를 사용한다.

## 7. 웹 제어 및 원시 로그

같은 네트워크에서 `http://bb-left.local/`로 왼쪽 보드의 제어 페이지에 접근할 수 있다. 이 페이지에서 알림 활성화, 민감도, 양쪽 보드의 상태 및 원시 로그 수집을 제어한다. 오른쪽 상태 조회에는 `http://bb-right.local/state`를 사용한다.

mDNS 이름으로 연결되지 않으면 시리얼 모니터에 출력되는 각 보드의 IP 주소를 확인한다. 제어 페이지의 오른쪽 상태 조회 주소는 코드에 `bb-right.local`로 지정되어 있으므로, 왼쪽 페이지를 IP로 열었다고 해서 오른쪽 조회까지 자동으로 IP로 바뀌지는 않는다.

| 경로 | 메서드 | 대상과 기능 |
| --- | --- | --- |
| `/` | GET | 왼쪽 보드의 제어 페이지 |
| `/state` | GET | 각 보드의 상태 및 업로드 진단 |
| `/toggle` | POST | 왼쪽 보드에서 알림 활성화 상태 변경 |
| `/sensitivity?value=...` | POST | 왼쪽 보드에서 데드존 설정 |
| `/recalibrate` | POST | 요청을 받은 보드의 자이로 재보정 |
| `/rawlog/start` | POST | 요청을 받은 보드의 새 원시 로그 시작 |
| `/rawlog/stop` | POST | 원시 로그 정지 |
| `/rawlog/download` | GET | 정지한 원시 로그의 CSV 다운로드 |
| `/rawlog/clear` | POST | 정지한 원시 로그 삭제 |

원시 로그는 LittleFS에 저장하며 `ts_ms,ax,ay,az,gx,gy,gz,tempC` 형식이다. 시간은 부팅 후 밀리초, 가속도는 g, 각속도는 °/s, 온도는 °C 단위다. 기록은 약 3분 또는 약 2 MB를 넘으면 자동 종료한다. 새 기록을 시작하면 이전 로그 파일을 덮어쓰므로 필요한 파일은 먼저 내려받는다.

원시 로그는 문턱값 조정이나 센서 상태 확인을 위한 짧은 수집에 적합하다. 이 데이터는 Google Sheets의 10초 집계값과 별도로 저장되며, 로그 저장 작업 자체가 측정 루프의 실행 시간에 영향을 줄 수 있다.

## 9. 적용 순서

1. 실제 보드의 출력 장치에 맞는 진동 또는 피에조 펌웨어를 선택한다.
2. 왼쪽 보드는 `#define ARM_IS_LEFT`를 활성화하고, 오른쪽 보드는 해당 줄을 주석 처리한다.
3. `ssid`, `password`, `scriptURL`을 사용할 네트워크와 Apps Script의 `/exec` 주소에 맞춘다. 두 보드는 같은 AP에 연결한다.
4. 스프레드시트에 연결된 Apps Script 코드를 `apps-script/Code.gs`로 교체하고 저장한다. 측정용 시트는 `Data`라는 이름을 사용하는 것이 명확하다. E열은 알림 팔 기록용으로 비워 두거나 `Alerted Arm` 제목을 사용한다.
5. 기존 웹 앱에서 **Deploy → Manage deployments → Edit → New version → Deploy**를 실행한다. 기존 배포를 새 버전으로 갱신하면 URL을 유지할 수 있다. [Google 공식 배포 안내](https://developers.google.com/apps-script/concepts/deployments)
6. ESP32-S3 대상과 올바른 L/R 설정으로 각각 빌드한 뒤 두 보드에 업로드한다. 스케치에 필요한 `.cpp`, `.h`, 다른 `.ino` 파일을 함께 유지한다.
7. 시리얼 모니터를 115200 baud로 열어 초기화 상태를 확인하고, 자이로 보정 중에는 팔을 가만히 둔다.
8. 양팔 측정 행, 알림이 있는 구간과 없는 구간, `Events`의 활성화 변경 기록이 예상대로 구분되는지 확인한다.

Apps Script를 먼저 갱신해도 기존 펌웨어의 측정 요청은 처리할 수 있다. 이 경우 새 펌웨어를 올리기 전까지 새로 들어오는 행의 알림 팔은 `Unknown`이다. 반대로 펌웨어만 먼저 바꾸면 기존 Apps Script가 새 `alerted` 필드를 저장하지 않으므로, 알림 팔 기록을 사용하려면 양쪽 변경을 모두 적용해야 한다.

## 10. 진단 및 검증 범위

시리얼의 `[window]` 로그는 측정 구간의 시작·종료, 지연, 큐 등록 여부와 누락을 보여 준다. `[upload]`는 실제 HTTP 전송 시작·종료, 소요 시간과 응답 코드를 보여 준다. 두 로그를 구분하면 측정 구간이 늦어진 것인지 전송만 늦어진 것인지 확인할 수 있다.

`/state`에서는 `telemetryReady`, `uploadBusy`, `uploadQueued`, `uploadDropped`, `uploadFailed`, `uploadUnconfirmed`, `uploadSucceeded`, `lastUploadMs`, `lastHttpCode` 등의 상태를 확인할 수 있다. 샘플 지연은 `maxSampleGapUs`, `sampleGapCount`, 기록 구간 지연은 `windowLateMs`, `windowMissedDeadlines`를 참고한다.

HTTP 2xx는 전송 계층의 성공으로 집계하며, 시트의 행 저장을 독립적으로 검증한 결과는 아니다. Apps Script가 오류 JSON을 HTTP 200으로 반환하는 경우에도 구분이 필요하다. 3xx는 저장 후 리디렉션일 수 있어 미확인으로 집계하며, 다른 HTTP 오류나 음수 결과는 실패로 집계한다. 최종 저장 확인은 실제 시트에서 수행한다.

2026-10-09 기준으로 ESP32 코어 3.3.5, `esp32:esp32:esp32s3` 설정에서 진동 모터 좌·우와 피에조 좌·우의 **네 가지 빌드가 모두 성공**했다. 측정 구간, 알림 경계·짧은 펄스, 업로드 큐 및 실패 상황을 다루는 네이티브 테스트와 Apps Script 모의 테스트도 통과했다. 세부 결과는 `ALERT_BUILD_RESULTS.json`에 기록되어 있다.

이 검증에는 실제 보드에 펌웨어를 올리는 작업이나 Apps Script의 실서비스 배포, 실제 진동·소리 및 Google Sheets 저장의 종단 간 확인은 포함되지 않는다. 적용 후에는 두 보드에서 측정 구간이 유지되는지, 상대 팔의 움직임에 따라 알림이 올바른 쪽에 발생하는지, 그 결과가 시트에 기록되는지를 함께 확인한다.
